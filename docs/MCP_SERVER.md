# Wobblepot MCP server

Wobblepot runs a remote [MCP](https://modelcontextprotocol.io) server, so an AI assistant such as Claude can answer "what is for dinner tomorrow" or "do we need milk" from the household's own data (HON-1151). With the user's permission it can also update the shopping list, the pantry and the meal plan, and add a household recipe: "we bought the milk", "add dish soap to the list" (HON-1154), "swap Thursday's dinner", "that was good" (HON-1174), "save our lasagne" (HON-1305). Every change it can make, the user can undo in the app.

Not to be confused with [MCP_SETUP.md](MCP_SETUP.md), which configures the MCP servers that agents working on this repository use.

## URL

| Environment       | MCP server URL                      |
| ----------------- | ----------------------------------- |
| Production        | `https://wobblepot.com/api/mcp`     |
| Staging           | `https://wobblepot.dev/api/mcp`     |
| Local development | `http://localhost:3000/api/mcp`     |
| Preview           | `https://<deployment host>/api/mcp` |

The resource identifier, the token audience and the URL are the same value: `getMcpResource(getServerBaseURL())` in `src/lib/mcp/oauth.ts`.

## Tools

Every tool has an `inputSchema` and an `outputSchema`, and the server lists every tool for every token. Each answers with compact JSON in a text block and the same object as `structuredContent`. Names of meals and ingredients follow the household's locale; dates are ISO `YYYY-MM-DD`; every `unit` is `g`, `ml` or `piece`, the unit the app shows.

### Read tools

These six carry `READ_ONLY_ANNOTATIONS`: `readOnlyHint: true`, `destructiveHint: false`, `openWorldHint: false`. A token with `mcp:read` can call them.

`get_household` (HON-1323) returns the setup behind what the other tools do: why `list_meals` leaves a meal out, why `plan_meal` refuses one, and where the default servings come from. Each name in `ingredientsToAvoid` lists the ingredient names it excludes, with the matching the planning filters use (`matchExcludedIngredients`, HON-1321); a name that matches none has an empty `excludes` and a `note` that says so. A member's `name` is the one the app shows (display name, then account name, then the member's own name), and `linked` is true when the member has an account. `servings.default` is `sumPortions` over those members. `rules` says in fixed text what each setting controls: allergens and ingredients to avoid filter `list_meals`, `plan_meal`, `swap_meal` and plan generation, the diet filters all of them but `list_meals` (`loadMeals` has no diet filter), while `restrictions` ("Notes for the AI") reaches only the AI prompts, so the assistant must check those notes itself. The members are read with a select that names each field (`listMembersForAssistant`), so no email, reminder, invite, token or AI cost cap can reach the reply; `get-household.test.ts` asserts the exact key set.

### Write tools

These twenty-two need the `mcp:write` scope as well (HON-1154, HON-1173, HON-1174, HON-1246, HON-1281, HON-1305, HON-1306, HON-1311, HON-1314, HON-1329, HON-1330, HON-1331, HON-1332, HON-1333, HON-1334, HON-1337, HON-1382, HON-1385). They carry `WRITE_ANNOTATIONS` (`readOnlyHint: false`, `destructiveHint: false`, `idempotentHint: true`, `openWorldHint: false`); `add_shopping_item`, `swap_meal`, `adjust_meal`, `change_meal_ingredients`, `create_meal`, `plan_meal`, `plan_fridge_meal`, `add_extra`, `remove_extra` and `remove_shopping_item` set `idempotentHint: false`; `clear_meal` sets `destructiveHint: true` and `idempotentHint: false`, because nothing restores what it deletes; `delete_meal` sets the same two, because it removes a recipe from the household's list and a second call refuses it. Each calls the service function its app route calls, with the same field schemas, so the two paths cannot drift. No row records which member or assistant made a change, because the models have no such field.

The pantry rules are the app's. Purchasing puts each ingredient in the pantry with an unknown quantity, in one transaction; an id that is not a global ingredient or the household's own refuses the whole call, so nothing is written. Undoing deletes the pantry item, but only one bought in the last 7 days. A staple keeps its pantry item and goes back to `0` ("ran out"), so it is on the list again (`ran_out`, HON-1398). Unlike the app's undo, the tool also keeps a pantry item with a quantity above 0 (`keepWithQuantity`): a purchase always leaves the quantity unknown, so the quantity is one the household entered, and deleting it would lose data the app cannot restore. A purchase replaces a quantity the pantry item held, so undoing that purchase removes the item; the purchase result gives a replaced quantity above 0 as `replacedQuantity`, so the assistant can tell the user and write it back with `set_pantry_status` `amount`. A quantity of 0 ("ran out") is removed as before. The app's own undo sends back the quantity its purchase replaced (`restoreQuantity` on `POST /api/shopping-list/unpurchase`), so the pantry item stays at that quantity, staple or not, and a tick undone by mistake keeps the amount the household entered (HON-1438). A quantity the household set after the purchase stays as it is (`has_quantity`). The result names every item it left. Checking a custom item that is linked to an ingredient also puts that ingredient in the pantry, and returns a quantity above 0 it replaced as `replacedQuantity`; unchecking does not restore it. `set_pantry_status` records what the pantry page shows: `have_some` writes quantity `null` ("have some, amount unknown"), `have_some` with `amount` writes that amount, and `ran_out` writes `0`. `amount` is above 0, in the unit `get_pantry` reports for the ingredient (`g`, `ml` stored as 1 ml = 1 g, or `piece`), so it needs no conversion. `amount` with `ran_out`, or any other `status`, fails input validation and writes nothing. A staple refuses an amount with an `isError` sentence and writes nothing, because completing a meal never takes a staple off, so its amount would never change. An amount lowers the shopping list by that much, and completing a meal takes its ingredients off it. Decided 2026-10-28 (HON-1402), which partly reverses HON-1201's "no amounts" of 2026-10-13: the household now sees and changes an amount on the pantry page, so it can correct one an assistant wrote. The tool creates the pantry item when there is none (not a staple) and otherwise changes only its quantity, so a staple stays a staple. Its output reports `quantity`, `null`, the amount or `0`, as `get_pantry` does. The shopping list reads only an unknown quantity (`null`) as purchased, so `ran_out` is never a purchase and puts the full amount back on the list. On a staple, `ran_out` puts it on the list now, with no amount when no planned meal needs it (`restock: true`, HON-1398). `have_some` takes the item off the list, as a purchase does, because the household has it. An amount set through the pantry API keeps the rest of what the plan needs on the list. Buying an item (`mark_purchased`, or checking a linked custom item) sets its quantity to `null`, replacing a `0` or an amount, so it drops off the list.

`swap_meal` and `rate_meal` find the entry by `date` and `mealType` in the household's own plan; a slot with no entry is refused, so neither adds a meal to an empty day (`plan_meal` does). `swap_meal` without `mealId` changes nothing and returns the list the app shows for that slot: the `/regenerate` list (current meal left out, ranked by closeness to it) when the slot has a meal, the `/suggestions` list when its entry is empty. Those lists leave out every meal planned from 14 days ago onward. With `mealId`, the meal is checked as `plan_meal` does (the shared `assertMealFitsSlot`, `src/lib/mcp/tools/meal-fit.ts`): for today or a later day, `isMealAllowedForSlot` checks that the household can see it, it suits the meal type, and it passes the household's dietary type, allergens and avoided ingredients; a past slot checks only that the household can see it (HON-1443). A meal planned recently is accepted, because a household that cooks from a rotation repeats meals on purpose and the 14-day window exists to rank suggestions, not to block a meal the user chose (HON-1392). The description tells the assistant to pass a named meal's `mealId` from `list_meals` in one call, without asking for suggestions first. `lastPlannedOn` gives the latest earlier day the household planned the meal, for `swapped` and `unchanged`, so the assistant can mention a repeat; it is `null` for `suggestions`. Any other meal is refused with `isError` and nothing is written. The write is the app's: tips, serving override, rating and the Adjust recipe note are reset and the entry's ingredient changes are deleted, so the description says that `set_meal_servings` sets the servings again; a skipped entry is planned again as the card does after a swap (HON-1125), and an entry that was cooked (`completed`) is never swapped, also when it was completed while the call ran. The meal already planned answers `unchanged`. On a past slot (before today in the household's timezone), the same write sets the entry `completed`, with no pantry change (HON-1382), and sets `pantryDeductedAt`, so a later revert and `cooked` never charge the pantry for it (HON-1391). The suggestions make no model call, so the tool counts only against the `mcp` limit, not the cost cap or the `meal-suggestions` bucket. `rate_meal` writes only the `rating` column, as the thumbs in the app do, and only on a cooked (`completed`) entry, the only place the app shows the thumbs, so the household can always see and clear what the assistant set. The write matches the entry's meal and status too, so a swap or a revert to planned that lands first does not take the rating with it.

`adjust_meal` is the app's Adjust recipe (HON-1244) without the review dialog. It refuses an empty slot and a cooked or skipped entry before any other work, then runs the adjust route's guards in the route's order: the `adjust-recipe` limit (30 an hour per household, on top of `mcp`), the `ai_generation_enabled` flag read with the caller's user id, and the household's AI cost cap. Each refusal is an `isError` sentence and writes nothing. Then one model call under `ADJUST_AI_BUDGET_MS` (30 s; the route declares `maxDuration = 60` for it); a provider error or the timeout answers the plain failure sentence. Every proposal whose replacement the catalogue matched, and every leave-out, is applied in one `replaceEntryChanges` write, with the instruction appended to `adjustmentNote` when all of it applied (otherwise no note, so the steps never follow a part the ingredients do not make), so the planner shows the Changed badge, the shopping list and the pantry deduction follow the entry, and the steps regenerate on the next open. A replacement the catalogue did not match is not applied, because the assistant has no ingredient picker: its name comes back in `unmatched` with the original it was for, and the assistant asks the user for another name. An ingredient the instruction named that the meal does not have comes back in `notInMeal`, and a name that fits several of its ingredients ("pepper" with black pepper and bell pepper) in `ambiguous`, so the assistant can ask which one. When the model proposed no change but the steps should follow the instruction ("less salt"), the stored changes are written back with the note only (`note_stored`). When it proposed changes and none could be applied (unmatched, missing or ambiguous), nothing is written: a note would make the steps follow a change the ingredient list does not make. `basedOn` is the stored change set, so a change the household made while the model ran refuses the write, and the tool asks the assistant to call again. The tool adds no prompt of its own.

`change_meal_ingredients` is the app's per-meal Replace, Leave out, Add an ingredient and Undo (HON-1243) for an assistant that names the ingredients (HON-1385). It makes no model call, so it counts only against the `mcp` limit: no `adjust-recipe` limit, no `ai_generation_enabled` flag, no cost cap, no `ai_usage` row. It refuses an empty slot and a cooked or skipped entry with `adjust_meal`'s sentences (`src/lib/mcp/tools/meal-changes.ts`). The changes become the rows the model would send: a `replace` of N ingredients is one `replace` row and N−1 `remove` rows, because "rice instead of potatoes and carrots" is one change to the user; the amount, given for the entry's effective servings as `get_meal` shows it, is divided by them, and `ml` counts as `g`, as the matcher converts it. `resolveProposals`, the half of `proposeAdjustment` after the model call, resolves and matches them, so both tools apply the same rules. A `restore` is the app's Undo: its name is matched, by the same name rule, against each live change's recipe ingredient, or the ingredient an added row brings in, and that row is left out of the new set; without it a left-out ingredient could not come back, because an add of a recipe ingredient is refused. Nothing is written unless every change applies, because half of a replacement gives a wrong shopping list the user may not notice: an unmatched or low-confidence replacement (`unmatched`, with up to three fuzzy alternatives in the household's language), a name the meal does not have (`notInMeal`) or that fits several of its ingredients (`ambiguous`), a replacement the meal or another change already brings in (`alreadyInMeal`), and a restore no live change fits (`notChanged`) each answer `not_changed`. A converted amount that crosses between pieces and weight by a guess, or that the matcher flags, answers `check_quantity` with the amount at the entry's servings, as `add_extra` does (`amountWarning`, `src/lib/mcp/tools/amount-warning.ts`). Otherwise one `replaceEntryChanges` write, with `basedOn` the stored change set and no note, so the steps follow the changed ingredient list.

`create_meal` saves one of the household's own recipes (HON-1305). The assistant cannot know ingredient ids, so it sends each ingredient as a name, a recipe-total quantity and a unit, and the server matches the names with `matchIngredients`, the matcher the app's import uses, with the household's id and locale. A guessed match gives a wrong shopping list that nobody notices, so the tool writes nothing unless every name matches with confidence: an unmatched name or a low-confidence match (`lowConfidence`) refuses the whole call with `outcome: unmatched`, each such name, its line as the tool built it, and up to three of the closest ingredients (the matcher's alternatives, or for a name with no match the top fuzzy candidates), in the household's language. The assistant asks the user and calls again with all the ingredients. A sure match whose amount the matcher flags (`quantityWarning`: over the guardrail for its category, or over 500 g a serving) also writes nothing, because the assistant converts units itself and a slip such as 500 `piece` for 500 g puts a wrong shopping list in place unseen (HON-1308). The call returns `outcome: check_quantity` and in `check` each flagged ingredient, its amount per serving in the unit the app shows (rounded to one decimal), and the matcher's warning text (English); the assistant asks the user and calls again with a corrected amount, or with the ingredient's `check` name in `confirmedAmounts` when the user says the amount is right, because a real amount can pass the cap (2 l of broth for 3 servings). A confirmed name, compared ignoring case, skips the check for that ingredient only. An unsure name is settled first, so a call with both kinds of row returns `unmatched`. Before matching, `findOwnMealByName` looks for one of the household's own recipes, not deleted, with the same name ignoring case and outer spaces; one found refuses the call with `outcome: exists` and that recipe's id and name. A shared catalogue recipe with the same name does not count, because a household's own version of a shared dish is normal. There is no unique index on the name, so two calls at once can both write; that race is accepted. The fields share their limits with the app's create route through `mealFieldsSchema` (`src/lib/meals/meal-fields-schema.ts`); the tool trims the name. A vague row is stored with no quantity, as the app stores it. Two names that match one ingredient are merged, as the matcher merges them; the merged row is unsure when either name was, so a guess cannot hide behind a sure match. The tool makes no model call, so it counts only against the `mcp` limit. It cannot change or delete a recipe; `update_meal` changes one.

`mainProtein` on `create_meal` and `update_meal` is the household's chosen main protein (HON-1387), stored as `proteinTypeOverride` (HON-1386), so the assistant can do what the recipe form does: mince with beans is planned as beef though the beans carry more protein. The description tells the assistant to leave it out unless the main protein is not the ingredient with the most protein, so the automatic value keeps its meaning. On `update_meal`, a missing key keeps the stored choice and `null` goes back to automatic. The rule is the lib's: the choice must be the protein type of a non-vague ingredient, of the new list when the call sends `ingredients` and of the stored one otherwise. `createHouseholdMeal` and `updateHouseholdMeal` refuse a choice that breaks it with `proteinTypeNotInRecipe` before they write, and the tool answers `outcome: check_protein` with `proteinTypes`, the distinct protein types of those ingredients (`distinctProteinTypes`), so the assistant asks the user, as for `check_quantity`. Ingredient matching runs first, so `unmatched` and `check_quantity` come before `check_protein`. A call that sends only `ingredients` without the chosen protein saves and goes back to automatic, as the form does. A successful result, and `get_meal`, return `mainProtein: { type, setBy }`: `type` is the stored `primaryProteinType`, and `setBy` is `household` when an override is stored and `automatic` otherwise, so a shared recipe is always `automatic`.

`update_meal` changes one of the household's own live recipes (HON-1314), through `updateHouseholdMeal`, the function the app's edit form PATCHes. A key the call leaves out keeps its stored value; `null` clears `preparationNotes` or `timeMinutes`. `ingredients` is the full new list and replaces every stored ingredient, so the description tells the assistant to call `get_meal` first and send the unchanged ones too. The list is matched by `matchRecipeIngredients` (`src/lib/mcp/tools/recipe-input.ts`), the step `create_meal` runs, against the new `servings` or the stored ones, and an unsure name or an unconfirmed flagged amount refuses the whole call with `unmatched` or `check_quantity` and writes nothing. Without `ingredients`, a `servings` change keeps the recipe's totals, as the app does (HON-712). A shared catalogue recipe, another household's, and a deleted one answer `notFound`. The app's edit route accepts a name another of the household's recipes has, so the tool does too and has no `exists` outcome. The update clears the cached prep tips and the image when their inputs change, and the tool deletes the cleared image after the update commits, as the route does. The result is the recipe as saved, read back with `getHouseholdMeal`, in `create_meal`'s shape. The tool makes no model call. To delete a recipe, the assistant uses `delete_meal`.

`delete_meal` and `restore_meal` (HON-1337) delete one of the household's own recipes and bring it back, through `deleteHouseholdMeal` and `restoreHouseholdMeal`, the functions behind Delete and "Recently deleted" on `/recipes` (HON-1336). A delete only sets `deletedAt` and keeps the ingredients and the image, so the recipe leaves `list_meals` and the Recipes page, and its planned and cooked entries stay on the plan, where `get_meal` still reads it. `restorableUntil` is the delete time plus `RECIPE_RESTORE_WINDOW_DAYS` (30), as a date in the household's timezone; after that the restore refuses and the purge cron removes the image. A shared catalogue recipe, another household's, an unknown id and a recipe already deleted are refused with the same message, so a call does not reveal that an id exists. `restore_meal` answers `unchanged` for a live recipe, and refuses one deleted longer ago than the window. The description tells the assistant to confirm the recipe with the user before it deletes it. Neither tool makes a model call.

`plan_meal` puts one meal the user chose in an empty slot (HON-1306), so an assistant can plan a week from the household's rotation: `list_meals` with `source: own` or `favourites` lists the household's own recipes or its favourites, and `plan_meal` places one per call. The day is any past day, today, or up to 28 days ahead in the household's timezone. A past day logs a meal the household ate (HON-1382): the entry is saved `completed` and the pantry does not change, because the household has shopped and adjusted it since. `pantryDeductedAt` is set, so the entry counts as already charged: setting it back to `planned` and then `cooked` never charges the pantry for a meal eaten days ago (HON-1391). A past day has no lower limit, so a meal logged late from a receipt is still correct. For today or a later day, the meal must be one the household can see, suit the meal type, and pass the household's dietary type, allergens and avoided ingredients: `isMealAllowedForSlot` runs the `getCandidates` filters of the slot suggestions for that one meal. A past day takes any meal the household can see (`isMealVisible`), because a log records what the household ate: a dinner eaten at lunch, or a meal outside the diet, is still what it ate, and the Past meals page takes it too (HON-1443). The 14-day no-repeat window of the suggestions does not apply, because a rotation repeats meals on purpose and the window exists to rank suggestions, not to block a meal the user chose; the app's own meal selector does not apply it either (decided 2026-10-24). Instead `lastPlannedOn` gives the latest earlier day the household planned the meal, so the assistant can mention a repeat. A slot with a meal, a note or a fridge meal is refused with a sentence that points to `swap_meal`; an empty picker placeholder is replaced, as in the app (HON-1251). A household with no plan row gets one, and no entry is cleared. Each refusal is an `isError` sentence and writes nothing. The tool makes no model call, so it counts only against the `mcp` limit. Plan generation (`plan_week`) is out of scope: it calls the model and replaces a week of entries.

`plan_fridge_meal` plans a fridge meal (HON-1281): a meal of what is at home, with no recipe, as the app's fridge-meal picker makes it (HON-1277). `get_meal_plan` returns such an entry with `kind: "fridge"` and its `items`, so an assistant reads it as a planned meal, not an empty slot. Each item's `name` follows the card's rule: the ingredient's name in the household's locale, the leftover meal's name (`null` when that meal was deleted since), or the free text; `source` is `pantry`, `leftover` or `text`. `entryId` on each entry is what a leftover item names as `sourceEntryId`. The source rule is `findLeftoverSourceProblem` (`src/lib/meal-plans/recent-meals.ts`, HON-1394): a recipe meal of this household, planned or cooked, not skipped, in an earlier slot than the fridge meal and no more than 3 days before its day. The window counts back from the fridge meal, not from today, so tomorrow's lunch can take tonight's dinner before it is cooked. A planned source needs `servings`, because the dinner's shopping list, pantry amounts, deduction and AI prompts then scale by its cook servings (`getCookServings`, `src/lib/meal-planning/servings.ts`): its own servings plus every leftover item from a fridge meal that is not skipped. A cooked source may omit `servings`, which then changes nothing. A fridge meal as source (it has no recipe), an empty slot, a later or same slot, an older meal or another household's entry refuses the call. The app's picker lists the same sources for its slot (`loadLeftoverSources`, HON-1396), the app's entry routes run the same rule, and Edit items and Undo send each item's `servings` back. The replace rule: an empty slot or an empty picker placeholder gets a new entry (`planned`); a slot with a planned or skipped recipe meal, a note-only card or a fridge meal becomes a fridge meal with these items in place of what it held, as the app's entry `PATCH` does (`replaced`); a cooked entry is refused, also when it completes while the call runs. On a past day, the new or replaced entry is saved `completed` with no pantry change and `pantryDeductedAt` set, as `plan_meal` logs a past meal (HON-1382, HON-1391). Completion of a planned fridge meal stays in the app: the tool does not change the pantry, and the assistant marks used-up items with `set_pantry_status` (decided 2026-10-26). Each refusal is an `isError` sentence and writes nothing. The tool makes no model call, so it counts only against the `mcp` limit.

`clear_meal` takes a meal off the plan (HON-1329), as Clear on a planner card does, so an assistant can act on "we eat out on Friday" or undo a `plan_meal` it got wrong. It finds the entry with `findPlanSlot`, as `swap_meal` and `rate_meal` do, and deletes it with `deleteEntry`, so the meal's ingredients leave the shopping list. A slot with no entry, an empty slot (`kind: recipe`, no meal) and a cooked entry are refused, also when it completes while the call runs, because the app offers Clear only on a card that is not cooked: a cooked entry records what the pantry was charged for and can be the source of leftovers. A planned or skipped recipe meal and a fridge meal that is not cooked are cleared. The entry's note, servings, rating and ingredient changes go with it, so the description tells the model to confirm with the user first, and to use `swap_meal` to put a different meal in the slot. The output names the cleared meal, or a fridge meal's items, so the assistant can plan it again with `plan_meal` or `plan_fridge_meal`. The tool makes no model call.

`set_meal_status` marks a planned meal cooked, skipped or planned again (HON-1330), as Cooked and Skipped on a planner card do (`use-entry-status.ts`), so an assistant can act on "we made the curry" and then call `rate_meal`. The tool says `cooked`, as the card's badge and `get_meal_plan`'s `isCooked` do; it stores `completed`. It finds the entry with `findPlanSlot` and calls `updateEntry` with the body the app sends: `cooked` on a recipe meal deducts the pantry (`deductPantry: true`, as Confirm in the deduction dialog does), `cooked` on a fridge meal passes `usedUpIngredientIds`, whose pantry items go to zero (ids not among the meal's items are ignored), and `skipped` or `planned` never deducts. The pantry is charged at most once per entry (`pantryDeductedAt`, HON-651), and going back to `planned` does not restock it; the description says so. A meal logged on a past day counts as charged, so `cooked` after a revert leaves the pantry alone (HON-1391). A slot with no entry and an empty slot are refused, and so is `usedUpIngredientIds` on a recipe meal or with a status other than `cooked`. A call for the status the entry already has writes nothing and returns `unchanged`, so the tool keeps `idempotentHint: true`. Every `EntryUpdateError` from `updateEntry` can only mean the entry moved while the call ran, so each maps to "The meal plan changed while this ran. Try again." `rate_meal`'s refusal for a meal that is not cooked names `set_meal_status`. The tool makes no model call.

`set_meal_servings` sets how many servings a planned recipe meal is cooked for (HON-1331), as the servings control in a meal's detail view does, so an assistant can act on "we have guests on Saturday, make dinner for 6". It finds the entry with `findPlanSlot` and calls `updateEntry` with `servingOverride`, with the limits of the app's `PATCH` (a whole number, 1 to 20); `null` removes the override, so the meal follows the household default again, which `get_household` reports. The recipe amounts and the shopping list follow the new count. The output's `servings` is computed as `get_meal_plan` computes it (`getEffectiveServings` of `sumPortions`), and `isDefault` is true when no override is stored. A slot with no entry, an empty slot and a fridge meal (no recipe to scale) are refused. A cooked meal is refused too, even for the count it already has, because the pantry was charged for its servings; `completedServings` from `updateEntry`, when the meal is cooked while the call runs, gets the same answer, and any other `EntryUpdateError` maps to "The meal plan changed while this ran. Try again." The same call twice leaves the same count, so the tool keeps `idempotentHint: true`. The tool makes no model call.

`remove_shopping_item` removes an item the household added to the shopping list by hand (HON-1332), as the trash button on the list does, so an assistant can act on "take dish soap off the list, we have some" or undo an item it added by mistake. Checking an item off is not the same: a checked item stays until Clear checked, and a checked item matched to an ingredient goes into the pantry. The tool reads the name with `findCustomShoppingItemName` first, so the output can say what it removed, then calls `deleteCustomShoppingItem`. An unknown id and another household's id get the same answer, "No item with this id. Use get_shopping_list to find it. Nothing was changed.", so another household's id is not revealed. Only `customItems` can be removed: the items from planned meals follow the plan, so the description sends the assistant to change the plan or to `mark_purchased`. An item a free-text extra put on the list is removed too, as in the app, and the extra stays on its day (`DayExtra.customShoppingItemId` is `SET NULL`). A second call with the same id is refused, so the tool sets `idempotentHint: false`. The tool makes no model call.

`set_favourite` adds a meal to the household's favourites or removes it (HON-1333), as the heart button in the app does, so an assistant can act on "add this one to our favourites" and build the rotation it plans from with `list_meals` (`source: favourites`) and `plan_meal`. Favourites also rank higher in swap suggestions. The tool reads the meal with `findVisibleMealName` first, in the household's locale, so the output can name it, then calls `addFavorite` or `removeFavorite`. The read is the check for both directions, because `removeFavorite` does not look at the meal: an unknown id, a deleted meal and another household's own recipe get the same answer, "No meal with this id. Use list_meals to find it. Nothing was changed.", and nothing is written. A meal that already has the asked-for state (`alreadyFavorite`, `notFavorite`) is not an error: it returns `unchanged`, so the tool keeps `idempotentHint: true`. The name is spelt `favourite`, as `list_meals`' `source: favourites` is; the output keeps `isFavorite`, as `get_meal` and `list_meals` do. The tool makes no model call.

`add_extra` and `remove_extra` (HON-1311) work on a day's Extras (HON-1309): a snack, a drink or another item outside the meals. `get_meal_plan` lists them in `extras`, for the same days as `entries`. `kind` is `ingredient` for a catalogue ingredient or `text` for free text; `quantity` and `unit` are the amount as the app shows it; both are `null` when the extra has no amount, and always for text. `add_extra` adds one extra per call, to a day from today to 28 days ahead, the range `plan_meal` uses (`writableDays` in `src/lib/mcp/tools/plan-slot.ts`). It matches `name` with `matchIngredients` as one item for one serving, so the converted amount is the whole extra in the ingredient's `defaultUnit`. A sure match saves an ingredient extra, which reaches the shopping list for its day as the app's does, unless its amount needs a check (`create_meal` refuses the same way, HON-1308): an amount that crosses between pieces and weight or volume, where Wobblepot does not know the weight of a piece (it would guess 30 g) or the matcher's `quantityWarning` flags the total, saves nothing and returns `check_quantity` with the converted amount and the reason. The assistant converts units itself, so that crossing is where a wrong amount reaches the list unseen; resending the amount in `check.unit` clears the check. A name with no sure match and no amount is saved as free text, which `createDayExtra` copies to the shopping list as a manual item linked to the extra (HON-1310). A name with no sure match and an amount saves nothing and returns `unmatched` with up to 3 alternatives, because free text holds no amount and saving it would drop what the user said. An amount in the ingredient's own unit is saved as given even when `quantityWarning` is set: the warning is a per-serving recipe guardrail (500 g a serving), and a day's 750 ml bottle of wine is not a serving. `remove_extra` deletes by id within the household; an unknown id, or another household's, is refused. A free-text extra's unticked shopping item leaves the list with its last linked extra, as with the app's Remove (`deleteDayExtra`, HON-1310). On a manual item, `get_shopping_list` gives `neededBy`, the earliest linked extra's day from today on, or `null`.

`set_extra_amount` (HON-1334) changes an ingredient extra's amount in place, or clears it with `quantity: null`, as the app's amount field does (`updateDayExtraQuantity`). Before HON-1334 the assistant removed the extra and added it again, which ran the name through the matcher a second time and took the shopping list line away between the two calls. `unit` must be the unit `get_meal_plan` shows for the extra (`displayUnit`): the tool does not convert, so it never guesses an amount, which is the guess `add_extra`'s `check_quantity` exists for. Another unit is refused with the right one named, for example "This extra is measured in ml. Send the amount in ml. Nothing was changed." An ingredient extra with no amount shows `unit: null` in `get_meal_plan`, so the description tells the model which unit fits (ml for a liquid, piece for a counted item, g for the rest), and a wrong guess comes back with the right unit. The amount is stored as given, because 1 g is 1 ml and the app's PATCH sends the shown number too. The tool reads the extra with `findDayExtra` first, within the household, for that unit. An unknown id, or another household's, is refused with "No extra with this id. Use get_meal_plan to find it. Nothing was changed." A free-text extra holds no amount, so it is refused and the assistant is told to use `remove_extra`, then `add_extra` with a name Wobblepot matches. The limit is `DAY_EXTRA_QUANTITY_MAX`, as for `add_extra`. The tool keeps `idempotentHint: true` and makes no model call.

**The scope check.** `runTool` (`src/lib/mcp/context.ts`) treats a tool as a write unless its annotations say `readOnlyHint: true`, so a tool that forgets its annotations is gated, not opened. A write tool called with a token that has no `mcp:write` answers `isError` with "This assistant can only read Wobblepot. To let it change the shopping list, pantry or meal plan, or add or change recipes, disconnect it and connect it again, then choose Allow." It runs nothing and is not counted against the rate limit. The tools are still listed for that token, so the model can tell the user what to do. `requireWriteScope(ctx)` is the check itself.

### Adding a tool

The tools live in `src/lib/mcp/tools/`, one file each, and `src/lib/mcp/server.ts` registers them. A new tool is a new file there plus one line in `MCP_TOOLS`. A write tool sets `annotations: WRITE_ANNOTATIONS` and calls the service its route calls; where the logic is inline in the route, move it to `src/lib/` first.

PostHog's MCP SDK adds a `context` argument (the agent's reason for the call), a `conversation_id` argument and an `llm_model` argument to every tool, and a small JSON block to results. That is expected; the SDK strips them before a tool runs.

## Protocol

Streamable HTTP, stateless: every `POST` builds a fresh server for that request (`createMcpHandler` from `@modelcontextprotocol/server`). It serves both protocol eras: the 2026-07-28 per-request envelope, and the 2025 `initialize` handshake (`legacy: 'stateless'`), because most clients still open with the second. `GET` answers 405, because no server-to-client stream exists. `OPTIONS` answers the CORS preflight; every response carries `Access-Control-Allow-Origin: *`, which is safe because the token is a bearer header and no cookie is read.

The server info (`mcpServerInfo(origin)` in `src/lib/mcp/server.ts`) carries `name: 'wobblepot'`, `title`, `version`, a one-sentence `description`, `websiteUrl` (the origin) and `icons`: `/icons/icon-192x192.png` and `/icons/icon-512x512.png` as absolute URLs on the origin. Claude shows the icon in its connector list; without it, Claude looks the host up in a third-party favicon cache, which can hold an old icon for weeks (HON-1171). Keep `name` and `version` fixed: `@posthog/mcp` reports them as `$mcp_server_name` and `$mcp_server_version`.

## Auth flow

1. The client calls `/api/mcp` without a token and gets 401 with `WWW-Authenticate` pointing at `/.well-known/oauth-protected-resource/api/mcp`.
2. It reads that metadata and the authorization server's at `/.well-known/oauth-authorization-server`, then registers (dynamic registration or a Client ID Metadata Document).
3. The user signs in to Wobblepot and allows the client on `/consent`. The page lists each requested scope in plain words; `mcp:write` reads "Update your shopping list, pantry and meal plan, and add, change and delete recipes." The user allows all the requested scopes or none.
4. The client exchanges the code (PKCE `S256`) for a 1-hour JWT access token bound to `<origin>/api/mcp`, plus a refresh token with `offline_access`.
5. Each `POST /api/mcp` carries `Authorization: Bearer <token>`; `requireMcpAuth` checks it against `/api/auth/jwks`.

The authorization server is in [SECURITY.md](SECURITY.md) → OAuth for MCP clients.

**Scopes.** `mcp:read` is required for every request (`requiredScopes` in the route); `mcp:write` adds the write tools. Both are in `MCP_SCOPES` (`src/lib/mcp/oauth.ts`), in the protected-resource metadata and in the 401 challenge (`challengeScopes`), so a client such as Claude asks for both. The challenge matters most: a client reads its `scope` before `scopes_supported`, and without `challengeScopes` it would say `mcp:read` only. A connection made before HON-1154 holds `mcp:read` only, and its refresh token cannot widen that: the user disconnects and connects again to allow changes.

**Adding a scope** takes two more steps than editing `MCP_SCOPES`, because the plugin stores scope lists in two places:

- Every registered client stores the server's scope list on its `oauth_client` row, and the authorize endpoint refuses a scope outside it with `invalid_scope`. A migration must add the scope to the existing rows (`20261013120000_add_mcp_write_scope`), or every client registered before the change fails as soon as it asks for the new scope.
- The `oauth_resource` row's `allowedScopes` narrows every token for `/api/mcp`. `resourceSeedMode: 'merge'` in `src/lib/auth.ts` rewrites it from config on each start. The default, `insertOnly`, never updates an existing row, so the new scope would be dropped from every token without an error.

## Connecting and disconnecting

My account → Connections (`/account/connections`) has a "Connect to an AI assistant" section (HON-1153): the server URL with Copy, three steps for Claude's custom connectors with a link to Anthropic's guide, and the "Connected assistants" list. The list is the user's `oauth_consent` rows (`GET /api/auth/user/mcp-consents`, `listMcpConsents` in `src/lib/mcp/consents.ts`).

**Disconnecting.** Disconnect calls `DELETE /api/auth/user/mcp-consents/[clientId]`, which deletes the user's `oauth_consent`, `oauth_refresh_token` and `oauth_access_token` rows for that client in one transaction (`disconnectMcpClient`). The plugin's own `/oauth2/delete-consent` deletes only the consent row, so it is not used. The access token is a JWT that is not stored, so deleting rows alone would leave it valid for up to an hour: `/api/mcp` therefore refuses a token whose `sub` and `azp` (the client id) have no consent row, with the same 401 `invalid_token` challenge as a deleted account. It also refuses a token whose `iat` is before the consent row's `createdAt`, so reconnecting the same assistant within the hour does not bring back a token issued before Disconnect. The assistant's next call fails, and it must ask the user to connect again. Another user's client id gets 404, so the route does not confirm that someone else's grant exists. Account deletion disconnects every assistant the same way (`docs/RUNBOOKS/gdpr-deletion.md`).

## Test locally with MCP Inspector

1. Run the app: `pnpm dev`.
2. Run the inspector: `npx @modelcontextprotocol/inspector`.
3. In the inspector, choose transport **Streamable HTTP**, URL `http://localhost:3000/api/mcp`, and connect. It follows the 401 into the OAuth flow, opens Wobblepot's sign-in and consent pages, and lists the tools once you allow it.
4. Call `get_meal_plan` with no arguments to see this week.

To call it by hand, take an access token from the inspector and send a 2025-era request (no envelope needed):

```bash
curl -s http://localhost:3000/api/mcp \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

`tests/e2e/mcp-read.spec.ts` drives the same flow in CI; `tests/e2e/mcp-write.spec.ts` connects with `mcp:write` and runs `mark_purchased`.

## Limits and errors

- **Rate limit.** 120 tool calls per hour per household (`mcp` in `src/lib/rate-limit.ts`), reads and writes together. `tools/list` is not counted. Over the limit, a tool answers `isError` with the reset time.
- **No household.** An account that has not finished onboarding gets `isError` with "This account has no household yet. Finish onboarding in Wobblepot first." from every tool.
- **No write scope.** A write tool called without `mcp:write` answers `isError` with the reconnect sentence (see Write tools).
- **Refusals** (an unknown meal id, a date range the wrong way round, an ingredient id that is not on the household's list) answer `isError` with a plain sentence.
- **Failures.** A tool that throws answers `isError` with "Wobblepot could not complete this request. Try again later." and reports the real error once through `captureApiError` (`src/lib/mcp/context.ts` → `runTool`). The server's error text never reaches the client.
- **CSP.** `src/proxy.ts` adds its Content Security Policy to this route as to every route. It is a header on a JSON response, which runs no script, and MCP clients do not apply it to a `fetch`, so it needs no exception.

## Analytics

`@posthog/mcp` wraps each request's server (`src/lib/mcp/analytics.ts`) and sends `$mcp_tool_call` per call and `$mcp_tools_list`, through `getPosthogMcpServer()`: a client of its own with the shared client's options, because `instrument` rewrites the library id (`$lib`) of the client it is given. Events are on the user's person (the token's `sub`) and carry `household_id`. A `beforeSend` removes `$mcp_parameters` and `$mcp_response`, so no search string, meal or pantry content reaches PostHog; `$mcp_intent`, the agent's reason, stays in full by decision; the sanitiser does not shorten `$`-prefixed keys. The SDK's exception capture is off: with SDK 2.x it only sees the error result, not the thrown error, so `runTool` reports failures instead. PostHog shows the results under MCP analytics.

The connect funnel is `mcp:server_url_copied` (Copy on My account → Connections, a client event, so the cookie banner gates it) → `mcp:client_connected` (Allow on `/consent`) → the first `$mcp_tool_call`. Disconnect captures `mcp:client_disconnected`. All three are listed in `src/lib/analytics.ts`.

The tool-call capture is server-side, so the cookie banner does not gate it, the same as `$ai_generation`. The consent page says what each event holds (the tool, its timing and the assistant's reason) and that the data the tool read is not recorded.

## Threat model

A token reaches one household's data and nothing else. It needs the `mcp:read` scope, is bound to this resource by audience and to one user by `sub`, and expires within an hour; a deleted account's token, and a token whose client the user disconnected, is refused even before it expires. The route resolves the household from `sub` on every request with `loadMcpCaller` (`src/lib/mcp/grant.ts`), which also checks the account and the grant and calls `getHouseholdMembership`, the call every API route makes, and each tool reads and writes only through that household's id (`get_meal` limits itself to the shared catalogue and the household's own recipes with `visibleMealWhere`; a write tool refuses another household's ingredient or item id as unknown, so it does not reveal that the id exists). A write needs `mcp:write`, which the user allowed on `/consent` after reading "Update your shopping list, pantry and meal plan, and add, change and delete recipes." The write tools change only the shopping list, the pantry and the meal plan, and add, change or delete the household's own recipes, and the user can undo each change in the app. `delete_meal` deletes a household recipe, which the household can restore in the app for 30 days (or the assistant with `restore_meal`); meals planned with it stay on the plan. A swap, and a fridge meal that replaces a planned meal (`plan_fridge_meal`), clear the entry's rating, tips, serving override, ingredient changes and Adjust recipe instruction, as the app's swap and fridge meal do; the user can plan the recipe again from the app. Like a swap, a clear (`clear_meal`) loses the entry's rating, tips, servings, ingredient changes and Adjust recipe instruction, and the user can plan the recipe again from the app. A confused or compromised client with write access can therefore mark items bought, add items, set a pantry quantity, or swap a planned meal or plan a chosen meal in an empty slot (only a meal that fits the household's diet and allergens, except on a past day, which logs any meal the household can see) or rate a cooked one, or plan a fridge meal of pantry items, a cooked meal's leftovers and free text in place of a planned meal, or clear a planned meal that is not cooked, or add or remove a day's extra, or change a planned meal's ingredients, or add, change or delete a recipe, within the shared rate limit of 120 calls an hour, but cannot change members or preferences. `get_household` sends the household's allergens, notes for the AI and member names, which can be children's, to the assistant; the consent page and the privacy policy name them. A recipe it adds or changes shows on `/recipes`, where the user can edit or delete it, and one it deletes shows there in "Recently deleted" for 30 days. `adjust_meal` is the one tool that calls an AI model, so it is the one that spends money: it is bounded by the `adjust-recipe` limit of 30 calls an hour, the household's AI cost cap and the 30 s budget, the same bounds as the app's Adjust recipe. The assistant's instruction reaches Anthropic, our processor, as the app's own Adjust recipe text does. Tool parameters and results stay out of analytics. What the assistant does with the data it reads is up to its own provider: it is a third party the user chooses, not our processor. The privacy policy says so (`/privacy#ai-assistants`), and the DPIA assesses it as risk area 3 (`compliance/dpia.md`, HON-1161).

## Not yet

A screen or script that only shows the meal plan or shopping list does not need this server: a read-only API key and `GET /api/v1/*` serve it without OAuth, and do not count against the `mcp` limit ([API.md](API.md), HON-1220).

AI tools such as plan generation are not planned yet. The household's AI cost cap is the per-household budget they need; `adjust_meal` runs under it.
