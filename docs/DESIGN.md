# Wobblepot design guide

> **Status: the current rules,** and `pnpm lint` enforces many of them. Core rules only. Read this before building or changing any UI. Rules cite the decision that produced them (`HON-NNN`) so the reasoning can be traced. Items marked **Proposed** describe where we want to be, not where the code is today.

**How to use this file:** judgment lives here in prose. Anything that can be checked mechanically (a token, a class, a component) lives in code, and this file points at it. When a review finds the same visual problem twice, name it in [Reject list](#reject-list) so agents recognise it instead of re-inferring it. Reviews check against the [Reject list](#reject-list) and [Composition rules](#composition-rules) only; a finding must name the item it matches, and anything this file does not name is taste rather than a finding (`HON-615`).

## Who we design for

- A tired parent at 5pm, holding a phone in one hand, deciding what to cook. Every screen must work at 390px width, thumb-reachable, with one obvious next action.
- Decisions are quick and repeated weekly. Familiar layout beats novel layout. Nothing should need learning twice.
- The AI is the engine, not the story. The interface shows meals, ingredients, and plans, never "magic".

## Type scale

Six levels for authenticated app pages (`HON-381`, raised one step in `HON-686`, Paragraph added in `HON-675`). Differentiate by color before size.

| Level     | Use for                                                                                                                            | Component                     | Renders as                         | Size / line |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- | ---------------------------------- | ----------- |
| Title     | Page heading: "Shopping list", "My recipes"; never a card title (HON-784)                                                          | `<Heading variant="h4">`      | `text-xl font-semibold`            | 22px / 30px |
| Section   | Day names, form sections ("Ingredients"), card titles under a page or dialog title (meal cards, HON-784)                           | `<Heading variant="section">` | `text-base font-semibold`          | 18px / 28px |
| Body      | Single-line items: meal names, ingredient rows, links                                                                              | `<Body variant="small">`      | `text-sm font-medium leading-none` | 16px / 16px |
| Paragraph | Multi-line foreground text: tips, notes, descriptions that are not secondary                                                       | `<Body variant="paragraph">`  | `text-sm leading-normal`           | 16px / 24px |
| Secondary | Helper text, descriptions, summaries; any text that wraps                                                                          | `<Body variant="muted">`      | `text-sm text-muted-foreground`    | 16px / 24px |
| Caption   | Meal-type labels, badges, quantities, day tags; form-group headings under a section title (`<Heading variant="caption">`, HON-781) | `<Body variant="caption">`    | `text-xs font-medium muted`        | 14px / 20px |

Two more levels exist for the cook view only (HON-932). It is read from a counter 50–70cm away, so its meal name and steps are a step up from anything else in the app. Nothing outside `MealDetailModal` uses them:

| Level   | Use for                                                                             | Component                     | Renders as                                          | Size / line                             |
| ------- | ----------------------------------------------------------------------------------- | ----------------------------- | --------------------------------------------------- | --------------------------------------- |
| Display | The cook view's meal name, its dialog title                                         | `<Heading variant="display">` | `text-2xl lg:text-3xl font-semibold tracking-tight` | 24px / 32px; 30px / 36px from `lg`      |
| Step    | The cook view's steps, "Watch out" and "Tip", and the household's preparation notes | `<Body variant="step">`       | `text-lg lg:text-xl leading-relaxed`, foreground    | 20px / 32.5px; 22px / 35.75px from `lg` |

**`text-xs` … `text-xl` are not stock Tailwind values.** They are re-based one step up in the top-level `@theme` block of `src/app/globals.css` (HON-686): `text-xs` 14/20, `text-sm` 16/24, `text-base` 18/28, `text-lg` 20/28, `text-xl` 22/30. The stock values (14px body, 12px captions) are a dashboard scale, and our reader holds a phone at arm's length. The names were kept so every primitive, variant and raw `text-sm` moves together, and so the next `text-xs` an agent writes lands at 14px rather than 12px. `text-2xl` and up are stock — only marketing, legal and error pages use them. Inputs keep `text-base md:text-sm`, now 18px on phones and 16px from `md`, so both halves stay at or above the 16px iOS no-zoom floor. `UI/Tokens` → `TypeScale` measures every value in Chromium, and the `title-scale` design rule reads its limit from a `text-xl` probe, so neither needs editing when a value moves — this table and the story's `TYPE_SCALE` do.

Rules:

- No arbitrary font sizes (`text-[10px]`). If a size is not in the scale, the design is wrong, not the scale.
- Do not override a `Body` variant's size, weight or colour with `className`. Pick the right variant and `tone`. Enforced by `shadcn/no-restyle` on every `pnpm lint` (HON-675); the handful of text-state classes still allowed on the type primitives are named, each with its reason, in `eslint.config.mjs`.
- `Heading` `h1`, `h2`, `h3` are for the marketing landing page, legal pages, error pages, and internal pages (`/status`, `/bot`, `/admin`). Inside the household-facing app, page titles are `h4`, with no exceptions for overlays or empty states except one: the cook view's meal name is `display` (HON-932), because that view is read from across a kitchen counter rather than held in the hand. The `title-scale` design rule exempts `data-variant="display"` and nothing else. Decided 2026-09-03, shipped in HON-607, which migrated the last five in-app `h2` components (`ShoppingEmptyState`, `MemberList`, `FirstTimeSetup`, `GeneratingOverlay`, `HouseholdSettingsForm`). Each kept its `<h2>` tag via `as`, so the size changed and the outline did not — except `GeneratingOverlay`, whose tag HON-619 moved to `<h4>` to sit inline beside the `h5` day labels, which were one level under the header wordmark's `<h4>`; HON-806 took the wordmark out of the outline, so the day labels are `h2` and the overlay is back to `<h2>`. `/household` was the last in-app page title still on the `h1` _variant_ — a bare `<Heading>`, which falls through to `defaultVariants`; HON-618 moved it to `variant="h4" as="h1"`, keeping the `<h1>` its outline needs. Once `MemberList` and `HouseholdSettingsForm` sat under that page `h1`, their `h4` titles made three Titles on one page, so HON-781 moved both to `variant="section"` (still `as="h2"`) and the form's group headings to `variant="caption"`. The rule now holds in code: this grep should return only the exempt page types (marketing landing, legal, `/bot`, `global-error`). It spans `src/components` as well as `src/app` — four of the five components named above live there — and matches an explicit `variant="h1"` and a `className`-only `<Heading>`, both of which land on the same `text-4xl` default.

  ```bash
  grep -rnE '<Heading( className=[^>]*)?>|variant="h1"' src/app src/components --include='*.tsx' | grep -v '\.test\.\|\.stories\.'
  ```

- Do not wrap `Heading` in `CardTitle` or `Body` in `CardDescription`. One component per text element.
- Visual level and HTML tag are separate choices. `variant` sets the size, `as` sets the tag. Pick the tag for document outline (no skipped levels, one `h1` per page) and the variant for the type scale. Decided 2026-09-03, shipped in HON-606. Omitting `as` renders the variant's natural tag, so for `h1`-`h4` only pass it when the outline needs a different level than the scale. `variant="section"` is the standing exception: its natural tag is `<h2>`, which is above almost every title a section sits under, so **every production `section` callsite passes an explicit `as`** — one level below the rendered tag of its enclosing title, read at the callsite rather than assumed. Shipped across HON-606, HON-613 and HON-619; this grep should return only stories, tests and prose:

  ```bash
  grep -rn 'variant="section"' src --include='*.tsx' | grep -v 'as='
  ```

## Spacing, radius, elevation

Spacing rhythm as used today (Tailwind steps, 4px each):

| Relationship                       | Gap                  |
| ---------------------------------- | -------------------- |
| Lines inside one card or list row  | `gap-1.5` to `gap-2` |
| Controls in a row, items in a list | `gap-3`              |
| Blocks inside a page section       | `gap-4`              |
| Between page sections              | `gap-6` to `gap-8`   |
| Page horizontal padding            | `px-4`               |

- One element owns each gap. Use `gap-*` on a flex or grid parent, not margins on children.
- Radius: `rounded-md` for controls (buttons, inputs, badges are `rounded-full`), `rounded-lg` for a `RowGroup` and dialogs, `rounded-xl` for `Card`. Do not mix within one component.
- Elevation: only overlays cast a shadow, with one exception for floating chrome: the header's pills take `shadow-float` (`--shadow-float` in the `@theme` block of `globals.css`, wide and faint, no offset; registered in `CUSTOM_SHADOW_VALUES` in `src/lib/utils.ts`) so they read as lifted off the page, and nothing else outside an overlay does. `shadow-md` on anchored overlays (select, top-level dropdown, autocomplete lists), `shadow-lg` on modal overlays (dialog, alert dialog, sheet) and the dropdown sub-menu, which stacks on top of its parent menu. Nothing in the page — controls, cards, badges, rows — has one; the border is the edge. HON-689 removed shadcn's default `shadow-xs` / `shadow-sm` from controls and `Card`, so a `shadcn add` can bring them back — strip them. The `no-content-shadow` scenario rule fails on any visible shadow outside an element with `role="dialog" | "alertdialog" | "menu" | "listbox"` or an overlay `data-slot` listed in `OVERLAY_SLOTS` in `src/stories/design-rules.ts` (a hand-rolled popover gets `data-slot="autocomplete-content"`; `card-content` and `collapsible-content` are in the page and are not listed); focus rings are spread-only and do not count. The grep below must return only overlays — `dialog`, `alert-dialog`, `sheet`, `dropdown-menu`, `select` (content only), `popover`, `tooltip`, `InlineAddItem`, `UnmatchedIngredientRow`, `IngredientSearch`:

  ```bash
  grep -rnE "shadow-(xs|sm|md|lg|xl)" src --include='*.tsx' | grep -v '\.stories\.\|\.test\.'
  ```

- Control height is `touch` (44px) below `md` and 40px from `md`, on `Button`, `Input`, and `Select` (`lg` and `icon-lg` 48 / 44px, `icon` 44 / 40px). `Input` has an `lg` size too, matching `Button` `lg` at 48 / 44px with `Button`'s 16px text at every width, for a field that sits beside `lg` buttons (the cook view's Ask field, HON-1022); the default field stays 18px text below `md` and 16px from it. HON-687 raised the `md` half from 36px: after HON-686 a `Button` label is a 16px font on a 24px line, and `py-2` around that line needs 40px — at 36px the line overran its padding box. Skeleton control bars mirror it as `h-touch md:h-10`. A skeleton's corner comes from its `shape` prop, named after what it stands in for (`default` for text and controls, `card`, `circle`, `checkbox`, `flush` for an image band), never from `rounded-*`. `sm` is for secondary inline actions; a screen's primary action is never `sm`.
- To change a control's height, pick a variant — never a `className`. Since those variants are responsive, a `className="h-8"` only overrides the base half: the variant's `md:` half carries a different modifier, so `cn()` keeps it, and Tailwind emits every `md:` utility in one media block after the base ones at equal specificity. The override therefore silently applies on mobile only, and the control is one height on a phone and another on a desktop. `sm` and `icon-sm` carry no breakpoint and are the fixed-height escape hatch (`button.test.tsx` asserts that). The same asymmetry applies to a `Select` trigger, where `data-[size=default]:h-10` also outranks a bare `h-8` on specificity alone — pass `size="sm"` instead.
- Interactive list rows and tab items are at least 44px tall on mobile. The floor has a name: `--spacing-touch: 44px` in `globals.css`, which yields `min-h-touch`, `h-touch`, and `size-touch`. Use those; never copy `min-h-[44px]` into a new row. `ShoppingItem` and `CustomShoppingItem` set it, and each tab item clears it at 56px off its own padding rather than an explicit floor. Shipped in HON-609. `UI/Tokens` → `TouchTarget` measures the token in a real browser, so CI fails if it stops resolving to 44px.
- A dense list on a page that is also used with a mouse may drop below the 44px floor on `pointer-fine:` only. The shopping list's rows are 44px on touch and 36px with a mouse (`min-h-touch py-2 pointer-fine:min-h-9 pointer-fine:py-1`, HON-1017), because a 39-item list at 52px was longer than it needed to be and the hover wash shows the row under the pointer. Key it to the pointer type, never the width: a touch tablet at `md` still needs 44px. Never use it for the controls in a dialog or for a primary action. `ShoppingItemSkeleton` → `AgainstLiveRows` measures the row.
- A new `--spacing-*` token must be added to `CUSTOM_SPACING_VALUES` in `src/lib/utils.ts` in the same PR that declares it in `globals.css`. Untold, `tailwind-merge` does not recognise the value as a member of the height/width/gap/padding groups and keeps both sides of a conflict, so every `className` override of it silently stops working — latent until something sizes a component with the token (HON-609 declared `touch`, HON-612 consumed it, PR #704 review found it). `utils.test.ts` fails if the two lists drift. Colour tokens need no such registration — `tailwind-merge`'s `color` scale is `isAny`. Radius does **not** get the same pass: its scale is `isTshirtSize`, so `--radius-sm/md/lg/xl` resolve only because they happen to be t-shirt names, and a `--radius-card` would repeat this bug with no guard to catch it. Same for `--text-*`, `--blur-*`, `--container-*` and `--animate-*`. `--shadow-*` got its list when `--shadow-float` arrived: `CUSTOM_SHADOW_VALUES` in `src/lib/utils.ts`, with the same drift test.
- Controls below the 44px floor are all deliberate, and all at 32px through a size variant, never a `className`, with one smaller exception: `icon-xs`, a 16px box whose `::after` reaches 4px past it on every side for a 24px target (WCAG 2.5.8), for an icon inside a line of small text. Its one user is `InfoTip`, the (i) after the nutrition line and the "Nutrition (per serving)" header (HON-930); `UI/InfoTip` → `Default` measures it. HON-612 raised the size variants (measured at 390px: `Button` default 44, `lg` 48, `icon` 44, `icon-lg` 48; `sm` 32 and `icon-sm` 32 by design), which reaches only elements that take their height from the variant. HON-688 moved everything that bypassed them onto one — the raw `<button>`s in `NoteEditor`, `CustomShoppingItem`, `MealRatingInline` and `RatingBadge`, and the `h-5` / `h-6` / `h-7` overrides in `MealCard`, `MealRatingPrompt` and `TimelineEmptySlot` — and HON-811 moved the one it missed, the meal detail's `ServingControl`, onto `Button` `ghost` `sm`, its colour on an inner span and a pencil after the text to show it opens a field (the cook view then raised it to `lg`, HON-932) — so what is left below 44px is `sm` and `icon-sm` by choice: card-row actions where 44px zones with a 6px gap would overlap. That covers `PantryItem` and `PantrySection` (star and trash at `icon-sm` for the 32px card-action rhythm), the `MealCard` and `CustomShoppingItem` actions, and the rating thumbs. Two text targets stay native `<button>`s because they wrap and every `Button` size is a fixed height a second line would overflow: `MealCard`'s meal name and `NoteEditor`'s note. Both carry `min-h-8`, so they hold the same 32px floor. `MealCard` puts Swap and Clear behind one `icon-sm` "More actions" menu next to Note, because three labelled `sm` buttons leave a 390px card too little room for the name. Stories measure the floor: `MealCard` → `Planned`, `MealRating`, `NoteEditor`, `CustomShoppingItem` → `Default`, and `ServingControl` → `Default` and `Overridden` (now at the 44px floor, HON-932). The close button of `Dialog` and `Sheet` is the last of them: the shadcn default wrapped a bare 16px icon, so the icon was the target, and it now composes `Button` `quiet` `icon-sm` at `top-2 right-2`, which leaves the icon where it was (HON-810). `MobileNav` raises its sheet's close to `size-touch`, because that sheet is the phone's account menu. `UI/Dialog` and `UI/Sheet` → `CloseButton` measure it. "Never a `className`" is now mechanical: `shadcn/no-restyle` denies `h-*`, `min-h-*`, `max-h-*` and `size-*` on `Button`, `SelectTrigger` and `Input`, so the next override fails `pnpm lint` rather than review (HON-674). The same pass moved the last control-sized override off `className`: the onboarding Adult / Child toggle had pinned itself to `px-3 text-xs` and now uses the default size.
- `Checkbox` and `RadioGroupItem` are 20px (`size-5`) by default, sized for the 16px body text they sit beside (HON-687); no callsite overrides the size. In `ShoppingItem` the `<label>` wraps the whole row (44px on touch, 36px with a mouse), so the real target is the row; in `CustomShoppingItem` the label covers only the 28px text block, so the checkbox is closer to a bare 20px target.

## Color

- Design in monochrome first. The neutral palette carries hierarchy through weight, size, and `muted-foreground`, not hue.
- Color adds meaning, never decoration. Every colored element also carries a non-color cue: an icon, a label, or a text change. The one exception is a meal's `imageHue`, which tints that meal's card and hero from its illustration; it is the only colour driven by data, and its lightness and chroma are fixed tokens. See [Imagery](#imagery).
- The only accent that exists is `primary` (near-black in light, near-white in dark). Do not introduce a brand hue in components ahead of a brand decision. A meal's hue is not an accent: it lives only on that meal's card and hero.
- Status has three generic tokens, each with a `-muted` tinted surface: `success`, `warning`, `info`. Use `text-success` for emphasis (text and icons), `bg-success-muted` for the surface, and `border-success/30` for a border — an opacity modifier on the emphasis token, not a token of its own. Red is not one of them: failure stays on `destructive`, so it never reads as one more status.
- Text colour on the type primitives is a prop, not a class: `Body` and `Li` take `tone` (`default | muted | destructive | success | warning | info`), and `Badge` has `warning` and `info` variants. `Badge` also has `surface`, `surface-success` and `surface-warning`: the page background as a pill, for a fact that is not the meal's own colour on a tinted card — the prep time, the pantry's verdict (`AvailabilityIndicator`). On the tint it is a white pill with no ring (the tint scope drops it); on the neutral card the `--border` ring is what makes it a pill. The meal's own badges (slot, protein, kid-friendly) stay on the chip colour. Decided 2026-09-24. `variant="muted"` stays the Secondary level and is the same as `variant="paragraph" tone="muted"`; `tone="muted"` exists for `variant="small" tone="muted"`, a single-line muted label. A tone does not exempt the caller from the non-colour-cue rule above. Form errors go through `FieldError`, which adds `role="alert"`. Decided 2026-09-23, shipped in HON-675.
- Domain names (available, missing, staple) stay in component props and copy, never in a token name. `AvailabilityIndicator` decides that "available" is success; the token does not know what it means.
- A `-muted` surface is for short, emphasis-coloured content: pills, badges, icon chips, callouts. It is **not** a panel fill for a block of body copy, because `muted-foreground` is calibrated for the neutral background — it measures 4.60:1 on white, so on any tint it lands at 4.3–4.5:1 and fails AA. A content panel that carries `Body variant="muted"` gets the border and no fill (`border-success/30`); the coloured icon and the coloured name already carry the meaning, and the fill was decoration.
- An unticked checkbox or radio draws its border in `muted-foreground`, not `input`: the boundary is the control's only cue, so it needs 3:1 (WCAG 1.4.11). `muted-foreground` re-scopes on every tint, so the border follows the surface (HON-1019). `src/components/ui/checkbox-contrast.test.ts` measures it on the background, the card and the note sheet in both themes.
- Never reach for a raw palette class (`text-amber-700`, `bg-green-100`). Every emphasis-on-muted pairing is measured at ≥5:1 in both themes; a hand-picked shade is unmeasured. `UI/Tokens` in Storybook renders every pairing as real text, so the axe gate re-measures them on each run.
- Never write a `dark:` override for a semantic token. Tokens already switch. There are no raw palette classes left under `src/**/*.tsx`, so a new `dark:` colour override means you have gone around the tokens.

  `shadcn/no-raw-colors` owns the _raw palette class_ half of this: it runs on every `pnpm lint`, covers the whole palette rather than the six hues below, and also catches a colour class naming a token that `globals.css` never declared — which is how `text-destructive-foreground` sat on two destructive dialog actions generating no CSS at all until HON-673 found it. It does **not** enforce the no-`dark:`-override half: `dark:text-primary` is a legitimate token reference as far as the rule is concerned, and `button.tsx` ships `dark:bg-destructive/60` deliberately. That half is still the greps plus review, and **both greps must return empty** (they also cover the runtime-assembled classes and the tests and stories the lint rule skips):

  ```bash
  grep -rnE "(bg|text|border|fill)-(red|green|blue|amber|orange|yellow)-[0-9]{2,3}" src --include='*.tsx' | grep -v stories
  grep -rnE "dark:(bg|text|border)-(red|green|blue|amber|orange|yellow)-" src --include='*.tsx'
  ```

## Motion

How often someone sees a motion decides whether it gets one. Our user repeats the same few actions every week on a phone, so the app should feel instant; motion is only for changes a person would otherwise miss. Decided 2026-09-14, adapted from the public `better-ui` and `emil-design-eng` skills, taking one value where they disagree and dropping what conflicts with this guide. Applied to the code in HON-665.

| How often             | Examples                                                                 | Motion                                              |
| --------------------- | ------------------------------------------------------------------------ | --------------------------------------------------- |
| Many times a session  | Ticking a shopping item, toggling a pantry staple, hover, switching tabs | None, or a colour or opacity change of 150ms        |
| A few times a session | Dialog, sheet, dropdown, select, toast, a newly added row                | The standard enter and exit below                   |
| Rarely                | A generated week appearing                                               | Same as above. No staggers or reveals for AI output |

- **Durations are a set, not a range:** 150ms for control feedback (press, hover, colour), 200ms for menus, dialogs, and every exit, 300ms for a sheet opening. No transition or one-shot animation inside the app runs longer; looping indicators (`animate-spin`, `Skeleton`'s `animate-pulse`) are not state changes and keep their own cycle. An exit is never slower than its enter. If a motion needs another value, the motion is wrong, not the set.
- **Easing:** `ease-out` for anything that enters, exits, or answers a press. `globals.css` overrides Tailwind's `--ease-out` to `cubic-bezier(0.23, 1, 0.32, 1)`, so the stock utility is the house curve and no one hand-writes a `cubic-bezier`. Never `ease-in`: it starts slow at the moment the user is watching. `linear` only for constant motion such as a spinner.
- **Name what transitions.** `transition-colors`, `transition-opacity`, or `transition-[…]` listing the properties. Never `transition-all`: it animates changes nobody meant to animate and hides which ones matter.
- **Transitions for state, keyframes for mount and unmount.** A state change on an element that stays mounted (toggle, press, hover, expand) uses a CSS transition, which retargets when reversed midway; keyframes restart from zero. Radix overlays are the exception and stay on `animate-in` / `animate-out`: Radix's `Presence` waits for a keyframe animation to end before unmounting, so a transition-only Dialog or Sheet would vanish on close without animating.
- **Nothing grows from nothing.** Overlays enter from `zoom-in-95` plus `fade-in-0`, never `scale-0`. Anchored overlays (dropdown, select, tooltip) scale from their trigger through Radix's `origin-(--radix-*-transform-origin)`; dialogs stay centred.
- **Press feedback.** `Button` scales to `0.97` on `:active`, except the `link` and `quiet-link` variants. It is the only press animation in the app, and it exists because a phone has no hover, so a tap is otherwise silent until the result arrives.
- **Theme switches snap.** `next-themes` runs with `disableTransitionOnChange`, and `ThemeToggle` swaps its icon without animating.
- **Motion is never the only signal.** Every animated change also changes a colour, an icon, or a label. Reduced motion (`globals.css`, HON-470) collapses every animation and transition to 0.01ms. `animate-spin` is the one exemption and keeps spinning, because a frozen spinner no longer says "loading".

The mechanical part is a grep. It must return nothing:

```bash
grep -rnE "transition-all|ease-in([\"' ]|$)|duration-([4-9][0-9]{2}|[0-9]{4,})" src --include='*.tsx' | grep -v '\.stories\.\|\.test\.'
```

## Imagery

The product supplies one piece of content imagery: a generated illustration of each meal. Photos a user attaches themselves (the recipe photos in `AttachImages`) are their input, not our imagery, and these rules do not cover them. The illustration is decoration. The meal name, ingredients, and steps carry everything the user needs, so the image never carries information and never gets in the way. It also gives each meal a colour: the card and hero take a tint from the food in the picture, so a week of meals reads as a week of different dishes before anyone reads a name. Decided in HON-726 (the image) and HON-743 (the hue, the tinted surface, and the blend).

- **One style, one source.** The only content imagery is the generated meal illustration, produced by the single prompt in `src/lib/meal-images/prompt.ts`: V4, a warm, stylised, gouache-like illustration of one serving of the finished dish on a pure white, flat surface, the plate taking about half the width of a 3:2 frame with empty space on every side. No stock photos, no second illustration style, no hand-placed decorative images, and no AI imagery anywhere else in the product. A second style or source is a second visual language the rest of the guide was not written for. The white surface is load-bearing: it is what lets the image blend into a tinted card (below).
- **Meal hue.** Every meal with an image has an `imageHue`: an integer from 0 to 360, the OKLCH hue of its food, extracted once when the image is generated and stored on the meal. It is the food's most **distinctive** colour, not its most common one: each hue bin's share of the meal's chroma is scored against `HUE_BASELINE` (the mean share over all stored meal images, in `src/lib/meal-images/colour.ts`), and the bin that most exceeds it wins, provided it holds at least 15% of the meal's chroma. Cooked food in the warm gouache style is mostly orange, so the most common colour gave a week of cards one amber tint; this way a salad gets its green and a tomato dish its red, while a brown stew stays orange because orange is all it has. It is the **only** per-meal colour variable. Lightness and chroma are never per meal, and nothing else about the meal (type, cuisine, tags) picks a colour. Components receive it as the `--meal-hue` CSS variable.
- **Tinted surfaces.** A meal card and the whole cook view take their background from `oklch(L C var(--meal-hue))`, with L and C fixed tokens:

  | Token                            | Light                              | Dark                               |
  | -------------------------------- | ---------------------------------- | ---------------------------------- |
  | Surface                          | L 0.97, C 0.035                    | L 0.35, C 0.035                    |
  | Text on a tinted surface         | `oklch(0.25 0.03 var(--meal-hue))` | `oklch(0.95 0.02 var(--meal-hue))` |
  | Muted text on a tinted surface   | `oklch(0.48 0.03 var(--meal-hue))` | `oklch(0.78 0.02 var(--meal-hue))` |
  | Accent chip (text: the text row) | L 0.90, C 0.11                     | L 0.27, C 0.11                     |

  The values live as `--meal-*-l` / `--meal-*-c` tokens in `globals.css`, and `[data-meal-surface]` there re-scopes the theme tokens (`card`, `foreground`, `muted-foreground`, `secondary` / `accent` as the chip, and `border` / `input` as the chip too, so no neutral line survives inside the tint) on the element that carries `--meal-hue`, so everything already inside a card uses the tinted values without a variant of its own. `src/lib/meal-tint.test.ts` measures every pairing against all 360 hues: the text and muted rows and the theme's `success`, `warning` and `primary` at ≥4.5:1 on the surface, and the chip at ≥5:1 like the status pairings. The dark surface is L 0.35, not the 0.45 the HON-743 contact sheet started from: at 0.45 the dark `success` / `warning` ingredient colours and the muted text fall below 4.5:1. The cost is that `multiply` on a dark surface darkens the food too, so in dark mode the image reads as a dim shape in the tint instead of a bright plate. That is acceptable for decoration, and a lighter surface would buy it back only by failing contrast. Fixed L and C are the point: every meal gets the same contrast, so one number is measured and tuned for all meals instead of one per dish, and no hue can produce an unreadable card. Text and chips on a tinted surface use these tokens, not the neutral `foreground` or `muted-foreground` values, which are calibrated for the neutral background (see [Color](#color)).

- **The image on a surface.** Rendered through `next/image` with `object-fit: cover` and `mix-blend-mode: multiply`, so the white surface of the illustration takes the tint and the plate sits on the card rather than in a white box. A `mask-image` linear fade blends its edge into the surface:
  - **Cards:** the image sits on the right at about 62% of the card width (45% on a card narrower than 448px, measured with a container query so a narrow grid column counts as narrow), and the fade runs left to right, reaching full opacity at 70% of the image width. The text sits on the plain tint to its left, and the title is capped in width so it wraps before it reaches the image. A card with an action at the right end of its first row (the planner card's menu, on the slot-badge row) reserves that column: the image ends before the action, so nothing read or tapped sits on the opaque illustration (`trailingActions` on `MealImageCard`, HON-749). The planner card's image is bounded by the card's head: every row from the slot badge down to the badge row (badge, title, description, availability, servings and rating badges), which sit at the left under the title's width cap and never touch it. Rows that run across the width below the head (a cooked card's rating prompt or inline thumbs) sit below the image on the plain tint, and the image ends where the first of them starts, with a short fade at its bottom (`head` on `MealImageCard`, HON-755, HON-927). A card with nothing below the head runs the plate to its bottom edge, unfaded. The note is not a row: its slip lies over the plate (see "Notes are sticky notes"), so a planned card with a note keeps the full-height plate. This is the one thing read or tapped on the image's opaque part, and only because the slip is opaque paper: its text is read on the paper, not on the plate (HON-974). A card taller than wide (the add-meal dialog's alternatives) uses the bottom layout instead: the image is a full-width 3:2 block below the content and above the actions, fading upward into the tint over its top 40%, and the title keeps the full row (`layout="bottom"`, HON-750).
  - **Modal hero:** the top of the cook view's steps column (HON-932, HON-966): 3:2 across the whole column, edge to edge with no radius of its own. Below `lg` the view is one column and the hero is still the first thing in it, above the title, across the full viewport width. From `lg` it tops the steps column, 3/5 of the panel, under the close button, and the title starts the left column, so the ingredients stay above the fold. Its height is capped at 45% of the viewport (`max-h-hero`), so a phone in landscape still shows the title; past the cap the frame gets wider than 3:2 and `object-fit: cover` crops the plate. The fade runs bottom-up into the tint. There is no top fade, because nothing sits above it. The panel it sits on carries the same tint, so the hero reads as the top of the meal's surface rather than a band across a neutral dialog.

  No border, no shadow, and no radius on the image itself: the card or hero clips it. A hard edge, a frame, or an un-blended white rectangle turns the illustration back into a photo pasted on a card.

- **Absence renders the neutral card.** A meal without an image renders the ordinary neutral card and no hero: no tint, no image element, no placeholder, icon, skeleton, or shimmer. A meal with an image but no `imageHue` (food with no chroma to take a hue from) renders the image **on a neutral surface** — the tint's lightness at zero chroma (`data-meal-surface="neutral"`), not the plain `--card`, which in the dark theme would multiply the image to near-black — on the card and the hero alike: a picture that was generated and paid for is never hidden by its colour. A placeholder tells the user something is missing when nothing is. The one exception is the hero while `imageStatus` is `generating`: a plain `bg-muted` box with the hero's 3:2 geometry holds the space so the content does not jump when the image lands. The box has no animation and no icon. Cards show nothing extra while generating.
- **Arrival is a fade.** The image fades in on load with `transition-opacity duration-200 ease-out` — the overlay duration and house easing from [Motion](#motion). Nothing else moves. On the hero the reserved box already holds the space. On a card the tint and text colours come from `imageHue`, which is stored with the image, so they are in place from the first render and only the image fades in.
- **Alt text is the meal name.** Nothing more — not "Illustration of …". A screen reader already announces it as an image, and the name is the only fact the picture adds.
- **Errors are silent.** A failed or unavailable image never produces a toast or error UI; the card or modal renders as if the meal had no image. The image is decoration and must not interrupt cooking.
- **Where.** Meal cards wherever they appear (the planner, alternatives, the household meal list, imagine results) and the cook view's hero. Not on ingredient rows, shopping lists, pantry items, or empty states: those are about ingredients and tasks, not dishes.

## Composition rules

Each of these came from a review that found the opposite in production.

- **Headings divide, borders contain.** Group items under a heading, not inside a bordered wrapper. A list draws one border per group: `RowGroup` (`src/components/ui/row-group.tsx`) boxes the group's rows and separates them with a divider, and the rows carry no border of their own. A bordered row inside a bordered group is the shape `HON-386` rejected.
- **No cards inside cards.** If a `Card` needs internal grouping, use spacing and a section heading (`HON-386`).
- **Past meals are rows.** `/past-meals` is a task list, so each meal is a `PastMealRow` in a day's `RowGroup` with one-click Cooked and Skipped, not a Today card (`HON-1007` → `HON-1018`).
- **The shopping list is one note sheet.** On Pantry & shopping the shopping list is one note sheet (`Card data-surface="note"`, the paper of Today's `UrgentShopping`) under the column's title and controls, which stay on the page level with the pantry's title and search. The sheet holds the Add field and the groups; the empty and load-failed states have no list and no sheet. The pantry stays on the neutral background. Inside the sheet rows are ruled (`RowGroup variant="ruled"`: no box, the rows' content on the heading's left edge), because a bordered group inside the sheet is a card inside a card. The rows have no dividers either: the group headings and the spacing already separate them, so a rule added lines and nothing else (`HON-1017`). The skeleton bars on the sheet are `Skeleton tone="soft"`, as quiet as the rows' hover wash. A half-viewport paper was tried and rejected (`HON-1012` → `HON-1016`): its edge crowded both columns and the empty yellow beside the list made the page lopsided.
- **Notes are sticky notes.** A meal note is the household's own writing on the plan, so it looks stuck onto the meal rather than part of the meal's data: a small yellow slip with a strip of tape across its top edge (`StickyNote`, `src/components/meal-plan/StickyNote.tsx`). The colour is `[data-surface='sticky']` in `globals.css`: the shopping note's hue, 95, at more chroma, with its own `--sticky-*` lightness and chroma in both themes, re-scoping `--foreground`, `--muted-foreground`, `--border`, `--input`, `--accent` and `--ring` inside the slip so nothing in it is neutral grey; `src/lib/meal-tint.test.ts` measures its pairings. The tape is that scope's `::before`, translucent with dashed ends and no blur. The slip is as wide as its text up to `max-w-xs`, tilted at rest (`--note-tilt`, -1° by default); a saved note is a button that straightens on hover and keyboard focus (200ms, none under reduced motion) and opens the editor in the same slip, straightened and full width, where the textarea has no border, fill or ring of its own and the slip's focus-within outline is the only one. The character counter appears only past 160 of the 200 characters. Read-only slots show the same slip, tilted and inert. The slip is paper, not a nested card: no border and no shadow, so "No cards inside cards" does not apply to it (`HON-926`). On a planner card the slip is laid over the card, not given a row: it lies over the head's bottom-right corner, on the plate, so a card with a note is the same shape as the card beside it without one (`overlay` on `MealImageCard`, `HON-974`). It keeps clear of the meal name, the ⋯ column and the badges: with a note, both badge groups in the head are capped at half the width, so a second badge wraps before the slip, and that extra badge line on a phone is the only height a note adds. The saved slip shows two lines at most, because the card has a fixed height to fit in and the shortest card (a one-word name, no description, no badges) has room for two; the editor opens in the same corner, may lie over the name while it is open, and keeps its field to one line that scrolls, so it fits that card too. A card without an image caps its title as an image card does, so the name wraps before the slip. The empty slot and the cook view have nothing to lie over and keep the slip in flow. On the planner card each slip rests at its own small offset and tilt from that corner, derived from a hash of the entry id so it is the same on every load and on the server (up to 8px left and up, 1–3° either way, `noteScatter` in `note-placement.ts`), so a column of noted cards reads as paper stuck on by hand rather than a layout element. The household can drag a saved slip anywhere on its card (Pointer Events, a press that moves under 4px is still a click) or move it with the arrow keys (8px, 32px with Shift, announced in the slip's accessible description), always inside the card and clear of its first row, so the ⋯ menu stays reachable. The place is saved on the entry for the whole household as fractions of the room the slip has to move in on the card (`noteX`, `noteY`; 0 flush with the left or top edge, 1 with the right or bottom), so a place set on a desktop lands in the same spot on a phone and stays on the card where the slip wraps taller; the slip keeps its width wherever it lies, and its tilt does not change on a drop. Clearing the note clears the place. Read-only cards show the slip at its offset, tilt and saved place, and cannot move it (`HON-975`).
- **The cook view is built for the counter.** `MealDetailModal` is what you open to cook a meal, and it still works when you only want to look at one (HON-932). It is read from 50–70cm away by someone glancing over between tasks, often with wet or floury hands, tapping with a knuckle. So:
  - **Near full screen.** Below `lg` it is the viewport (`DialogContent size="fullscreen"`: `inset-0`, `h-dvh`, no radius, padded by the safe-area insets through `p-safe`). From `lg` it is a panel 24px in from the viewport edges (`inset-6`, `rounded-xl`), so the dimmed plan still frames it and it still reads as an overlay.
  - **The whole panel is the meal's surface.** `data-meal-surface` and `--meal-hue` sit on the panel, with `MealImageCard`'s rules: a hue tints it, an image without a hue gets `neutral`, and no image (or one still generating) leaves the plain background. Everything inside uses the re-scoped tokens. No grey tips box and no divider: the steps sit straight on the tint.
  - **Order.** Below `lg`, one column: hero, title row (Display name and the ⋯ menu), description, time (the cards' `surface` clock badge, HON-951), Kid-friendly and, for one of the household's own recipes, "My recipe" (HON-953), the note when there is one, ingredients (then "Staples"), nutrition with its disclaimer, "You'll need" (the equipment), then the steps (the household's notes first, then the numbered steps, "Watch out" and "Tip"), so "Done cooking" ends the view. From `lg` (not `md`: a portrait tablet keeps one tall column), two columns that each scroll on their own, so scrolling the steps never moves the ingredients: the title row down to nutrition on the left (2/5), and the hero, "You'll need" and the steps on the right (3/5). Without a hero the first heading of the right column sits on the meal name's line (HON-951). "You'll need" is what a cook sets out before step 1, so it sits directly above "Steps" in both layouts, at the same heading level, not with the ingredients (HON-966). Both columns are `display: contents` below `lg`, so their children join the single column in DOM order, and what a screen reader hears is what the page shows (WCAG 1.3.2, HON-965). The hero is the one exception: it is in the steps column in the DOM and moved first with `order-first` below `lg`, so a screen reader meets it after the nutrition. Its alt text is the meal name, so nothing is lost (HON-966).
  - **Type.** Display for the name and Step for the steps (see [Type scale](#type-scale)); section headings are Title (`h4`, rendered `h3`); ingredient rows are 18px with the quantity first, in a fixed-width `tabular-nums` column so the names line up. Nothing is below 16px except the nutrition line and its disclaimer, so badges in the view take `Badge size="lg"`.
  - **Targets.** Every button is 44px or more (`lg`, `icon-lg`), including the serving control, the ⋯ menu and the note's buttons. Each ingredient row is a `label` around a 24px `Checkbox size="lg"`, at least 44px tall, so a tap anywhere on it toggles the pantry. The close button is a 44px+ chip-token disc, always at the top right. On a phone a bar takes the tint and shows the meal's name once the title scrolls under it.
  - **Focus.** The panel itself takes focus on open, not its first control, so neither a keyboard nor a focus ring pops up. The scroll regions are focusable so a keyboard can scroll them.
  - **Steps are just there** for a planned meal (HON-933): they come from the server's cached copy, or are generated as the view opens, with "Writing the steps…" over the skeletons. A failure stays until Retry, so reopening never loops on it. A completed, skipped or read-only entry keeps "How to prepare", because nobody is about to cook it.
  - **A step is a toggle.** The whole row is a 44px+ `button` with `aria-pressed`. A done step shows a check instead of its numeral and its text goes muted, never struck through. The first step not done sits on the chip token, with its numeral on the page background, so a glance finds your place. The progress is not saved: it lives as long as the page does, and new steps (a swap, a serving change) start unticked.
  - **Ask about a step or a piece of equipment** (HON-969, HON-983). On a planned entry the household can edit, each step row ends in a ghost Ask button (`MessageCircleQuestion`, "Ask about step {n}"), a sibling of the step toggle and never inside it. Below `lg` it is the `icon-lg` icon alone, at stroke 2.25 so the outline reads from the counter, because the phone row needs its width for the step text; from `lg` it reads "Ask" beside the icon (size `icon-lg-to-lg`, HON-981). At every width a shadcn `Tooltip` (`TooltipContent size="lg"`, 16px) shows "Ask about step {n}" on hover and on keyboard focus, and the accessible name stays that full label, which contains the visible "Ask". The focus that a tap or a click on Close returns opens no tooltip, because on a phone it would cover the step until the next tap. No `title`. With its panel open it stays the Ask button, with `aria-expanded`, and takes the `secondary` fill, the current step's surface, so the open row is plain to see; Close is in the panel (HON-1022). The steps' Ask buttons end on the same edge as the ones in "You'll need": the step rows bleed left past the numerals (`-ml-3`), never right. Ask opens a panel directly under that step, indented to the step text and ending at the Ask buttons' edge, straight on the tint with no card and no border. It reads top to bottom in the order things happen (HON-1022). Before a question: three `outline` `lg` chips that send at once ("How do I know it's done?", "What can I substitute here?", "I'm short on time"; they are actions, so not `ChoiceChips`), a field with Send in a form, so Enter sends, and a footer row with Close. The chips, the field (`Input size="lg"`) and Send (`lg`) are one height, with 16px text. Once a question is sent, the chips go and the panel reads: the question itself, "You asked: {question}", muted and one size below the step text (`Body variant="step-small"`), with a ghost `lg` Edit directly after its text (HON-976); the answer at the step size, or the error's catalog copy; a follow-up field with Send, placeholder "Ask a follow-up", because the next question builds on this one (HON-980); and the footer row, with "Thinking…" while pending or Retry when a retry can help at its start and Close at its end, under Send's edge, so Close never moves. The question line shows while pending, with the answer and with an error, and a chip's question needs no mark of its own because the line names it. A chip that sends moves focus to Close before it unmounts, as Retry does; never to the field, which would open a phone's keyboard. Closing the panel discards the question, so the chips are back when it opens again. Edit puts the question back in the field, focuses it with the caret at the end, and does not send; sending the edited text is a new typed question. Send stays `aria-disabled`, not `disabled`, while pending, so a second tap cannot bill a second call. The answer streams in (HON-979): its first words replace "Thinking…" as soon as the model writes them, and the rest grows in place. Send stays `aria-disabled` until the stream closes, and the status is `aria-busy` meanwhile, so a screen reader reads the finished answer once. A stream that breaks after its first words keeps them, with the generic error and Retry under them. One panel is open at a time, across the steps and "You'll need". Marking the step done closes its panel and discards its question and answer, because the cook has moved on; focus stays on the toggle, and un-marking the step reopens nothing (HON-982). Marking another step done leaves the panel as it is. One question has one answer: a new question replaces both, and closing the panel or opening another step's panel discards both. The replacement waits for the new answer (HON-978): while it is on its way the old answer stays, muted, under its own question line, "Thinking…" shows in the footer row before Close (so it adds no line), and the new answer or the error takes the old answer's place. Keeping the old text is what holds the panel's height, so the steps below do not jump up on send and back down on arrival; there is no reserved height. Nothing is saved. Close, or Escape in the field, returns focus to that step's Ask button; switching to another step's panel moves focus into its field; an answer arriving moves no focus. It does move the view (HON-977): the panel scrolls into view as it opens, and the answer or error, with the follow-up field and Close under it, scrolls into view as it arrives and again when the stream closes, with `block: 'nearest'` so a panel already in view stays still, and a snap instead of a glide under reduced motion. Each row of "You'll need" ends in the same Ask button, a sibling of the item text, named and tooltipped "Ask about {item}" (HON-983), because "I don't have a wok" belongs to the wok, not to the step that uses it. Its panel opens under the row and starts at the item text, as there is no numeral to indent past. It is the step panel with its own chips ("What can I use instead?", "Does the size matter?", "Can I skip it?") and the placeholder "Ask about this item" before a question; the rest, from the follow-up field to Escape and streaming, is the same. The answer names the steps that use the item and says what a substitute changes in them, and never suggests buying anything.
  - **"Done cooking" ends the view**, after Watch out and Tip, on a planned entry the household can edit. It closes the view first, then runs the entry's completion (`useEntryStatus`, shared with the past-meals row): the pantry deduction, then the rating prompt. The two dialogs never stack, and focus ends on the card's meal name. A completed card offers "Not cooked yet" in its more-actions menu as the way back; past meals are marked on `/past-meals` (HON-1018).
  - **The screen stays on** while the view is open (`useWakeLock`, best effort and silent), and sleeps again when it closes.
  - **The nutrition disclaimer stays visible**, directly below the macros, at the end of the ingredients, never behind an icon (HON-466).
- **Actions sit on the title row.** A card's actions align right on the same line as its name, in one row, never as a footer strip or stacked buttons (`HON-378`, `HON-383`). The rule covers actions that act on the card's subject (Swap, Clear, Add note). When they would crowd the name, the frequent, reversible one stays a direct button and the rest go behind one `icon-sm` ⋯ "More actions" menu named for the card: the planner's `MealCard` puts Note, Swap and Clear in it, and the recipe library card keeps the favorite heart and puts Edit (a link) and Delete in it (`HON-934`). The cook view follows the same rule at its own size: "Add note", or "Edit note" when there is one, sits behind an `icon-lg` ⋯ menu on the title row beside the meal name, because every target in the view is 44px, and no standalone "Add note" button sits between the badges and the ingredients (`HON-966`). One exception, scoped to lists: a panel that shows the first part of a longer list may end with a single continuation row that links to the rest. That row is the list's own last line, not a card action, and it says what is past the cut ("Plus 8 more for the next 5 days", Today's shopping panel). When nothing is past the cut but the full list is still the only place to act on the items (checking them off), the same row reads "View full list", so the link stays in one place instead of hopping to the title row as the week fills. It is a single muted text link at the item size, never a button or a strip of buttons (`HON-928`, `HON-947`).
- **A card carries its own slot label.** The meal type ("Dinner") is the planner card's first row, as a `secondary` `Badge` (`MealTypeBadge`), inside `MealCard` and `TimelineEmptySlot` alike, so the card still says what it is when the slot has an illustration behind the title or when it is read on its own. This reverses `HON-379`, which put the label above the card as a caption: with the tinted surface the caption floated between cards and belonged to neither. Decided 2026-09-24.
- **The whole planner card opens the cook view.** A pointer click anywhere on a meal card (the plate, the description, the empty tint) opens `MealDetailModal`, as the name does (HON-1010). Every control on the card keeps its own click, the saved note's slip and the open note editor included; a read-only card's slip is part of the card. A click that ends a text selection opens nothing. The name stays the card's keyboard target and accessible name; the card itself takes no role and no tab stop. On hover the name underlines and the border turns the muted text colour over 150ms, with no shadow; when the name has keyboard focus, the card draws the focus ring around itself (`Card interactive`, `data-slot="card-target"`). The empty slot has no meal to open and no card click.
- **Content is not sticky.** Action bars live inline at the end of the content they act on. The only fixed chrome is the header and the mobile tab bar (`HON-380`). The tab bar is opaque `bg-background` like the header's pills, with no backdrop blur: page content scrolls under it and never shows through (`HON-809`). They stay put when a Radix overlay locks page scroll only because `globals.css` sets `scrollbar-gutter: stable` on `html` and zeroes the lock's body margin — keep both (`HON-690`).
- **The header floats.** The fixed bar at the top is transparent and lets clicks through; the chrome sits in pills on it, opaque, `rounded-full`, bordered, `h-12` under a `pt-4` offset. From `md` up there are two, the logo with the daily views left and the settings views with the account menu right, 16px in from the viewport's edges (not the content column's: the chrome belongs to the window, the column to the page) with the page showing through between them; on a phone one pill spans the column with the logo and the account icon at its ends (`HeaderChrome`). Scrolling folds the logo away: its box narrows to nothing as it fades, the daily views slide left and the pill closes around them, and on a phone the pill draws in to a disc around the account icon; it unfolds once the page is back at the top (`useScrolled`, with hysteresis so it cannot flicker). The right pill folds too: My recipes and Household close to their icons (`BookOpen`, `Users`) as the labels narrow away, and hovering a link (or focusing it from the keyboard) opens that link's label beside its icon, one at a time; the label is clipped, never hidden, so it stays the link's accessible name (`NavLink` in `navigation.tsx`). Below `lg` the right pill rests folded as well: at 768px the two pills with every label open do not fit once the first link reads "Meal plan", and a portrait tablet has no hover to lose (HON-924). Nav links are Section size (`text-base`, 18px) and the full pill height, so the hover zone is the band, not the line of text. A pill that holds only the logo fades out rather than surviving as an empty ring. 300ms on the house curve, properties named, snapped under reduced motion. The pills are bordered and carry `shadow-float`, the faint wide lift that is the elevation rule's one exception outside overlays, so they sit just off the page the way toggl.com's do; on the dark background the shadow disappears and the border is the edge. The current link is marked by colour and `aria-current` alone, because an underline read as a second edge under the curve, and every control inside a pill is `Button` `shape="pill"`: Sign in a ghost, Sign up the one filled pill, the account and theme icons ghost discs, so no `rounded-md` hover box or control border sits inside the pill's. Decided 2026-09-25. The band stays 4rem tall (offset plus pill), so `main`'s top padding and the `*-below-header` utilities in `globals.css` did not move.
- **Buttons are as wide as their label.** On a phone a page-level button fills the column, because a 44px target across the width is easier to hit. From `md` up it is as wide as its label and aligns to the start of its column: `w-full md:w-auto`, plus `md:self-start` in a flex column (as the cook view's "How to prepare" does, HON-932). A pair of actions is two-up on a phone and label-sized at the start of the column from `md`, in the order Cancel, confirm (`MealForm`). The auth, `/onboarding` and `/invite/[code]` form cards are the exception: there the card is the form, and the button is the form's width. The first-run card on Today (`FirstTimeSetup`) is an in-app state, not onboarding, so it follows the rule and its button lines up with the chip groups above it (`HON-767`, `HON-782`).
- **A pick-one choice is a radio group.** A row of chips where exactly one is chosen (onboarding's Adult / Child, the first plan's start day and length, the member dialogs' portion presets) is `ChoiceChips` (`src/components/ui/choice-chips.tsx`), never a row of `Button`s with a swapped `variant`. It exposes the choice as `radiogroup` / `radio` with `aria-checked`, gives the group a name, and marks the selected chip with a check icon as well as the fill, so the state is not carried by colour alone. `Toggle` is for independent on/off controls, not one-of-many (`HON-828`). A row of on/off chips beside a pick-one row (the household allergens) is `Toggle` with `variant="outline" tone="primary" size="chip" indicator`, so a pressed chip looks like a chosen one and carries the same check icon (`HON-962`).
- **One page width.** Content is centered and capped at 1152px. Tables and lists may fill it; prose stays narrower (`HON-376`). What sits inside that width is set by the four page-shell rules below (`HON-767`).
- **No page-level Card.** A `Card` groups one section of a page or is the item itself (a meal); it never wraps a whole page. A page's outer structure is the page container (`w-full px-4 py-8`, as `src/app/household/page.tsx` has it) and its headings. `main` already caps and centres the column at `max-w-page`, so the container adds only the gutters; Tailwind's `container` is not used, because its breakpoint max-widths inset the page from the footer between 640px and 1279px (`HON-843`). Exception: auth, onboarding and invite pages are a single form and keep their centred form card, because there the card is the form, not the page (`HON-767`).
- **Titles sit on the page background.** A page whose content is one thing (`/recipes`, `/profile`, `/household`) opens with `Heading variant="h4" as="h1"` and an optional `Body variant="muted"` line directly on the background, above the content. A page that is a workspace of sections (Today, `/shopping`, `/pantry`) titles its sections, not the page; each section title sits on the background too, rendered `as="h2"`, with the section's `RowGroup`s the only bordered things under it (`ShoppingListHeader`, `PantrySection`). A workspace page still has one `h1`, visually hidden, so the outline starts at level 1 and the screen does not change: `<div className="sr-only"><Heading variant="h4" as="h1">` first inside the page container, ahead of every `h2`. Today's reads "Meal plan" (`TimelineView`, and `FirstTimeSetup` for the first-run state), not "Today", which is already the first day card's heading; `/shopping` and `/pantry` share "Pantry & shopping", the desktop nav label, in `InventoryPage` (`HON-815`). This reverses the `HON-767` shape, where the two `/shopping` columns were `Card`s with the title in their `CardHeader`: at 390px the card's padding took 48px of the 358px column and its edge ran along the viewport edge, so the section card read as the page-level card the rule above forbids, and the bordered rows inside it were the first item on the [Reject list](#reject-list). Decided 2026-09-25. A page has one Title: columns or groups under it use Section, and groups under those use Caption, so no heading renders at its parent's size (`/household`: page `h1` at Title, then four `h2`s at Section — Members, Household details, Food preferences, Meals to plan — and no `h3`, `HON-960`; it was two column `h2`s with Caption `h3` groups under the form's in `HON-781`). A card is a section of the page or dialog it sits on, so its name never carries the Title level either: `MealCardBase` renders the meal name at Section on `/recipes`, in the imagine results and in the swap and imagine dialogs, with the tag still chosen by the caller for the outline (`HON-784`).
- **Lists fill, forms stay narrow.** A page whose content is a list or a workspace (`/`, `/shopping`, `/household`, `/recipes`) fills the page width. A page whose content is a form or prose (`/profile`, legal pages) keeps a `max-w-2xl` column, left-aligned inside the container, not centred in the viewport (`HON-767`). `/household` is both: the member list comes first and fills the width, and the settings follow in one `max-w-2xl` column below it, not in a half-width column beside it (`HON-960`).
- **Content starts at the top.** No `place-items-center` shells for in-app pages: the content column aligns to the top of the container, so a page's height can change (loading → loaded, empty → populated) without moving what is already on screen. The route's `loading.tsx` uses the same container and column width, with no bordered wrapper standing in for a card the page does not have (`HON-767`).
- **Controls belong in menus, not headers.** Preference toggles (theme; language is a household setting on `/household`, not a per-user preference) live in the user menu, not in the header bar (`HON-382`, `HON-775`). The one exception is the signed-out header, which has no user menu: there the theme toggle sits in the right pill beside Sign in and Sign up, as a ghost disc like the account icon it stands in for, until a session gives it a menu to move into.
- **The account menu is a person.** On every viewport the account entry point is the person icon; the bottom tab bar is the only main navigation on a phone (`HON-775`).
- **Four tabs on a phone.** Plan, Shopping, Pantry, Recipes. Household and Profile live in the account menu. A fifth tab is not an option; a new destination replaces one of these or lives inside one (`HON-776`).
- **Mobile first, then widen.** Build the 390px layout, then add `md:` and `lg:` variants. Never the reverse (`HON-395`).

## Copy

Full voice guide: [docs/PROJECT_SPEC.md → Brand voice and tone](PROJECT_SPEC.md#brand-voice-and-tone). The operational rules:

- Sentence case everywhere. "Add meal", not "Add Meal".
- Actions are imperative verbs: "Add meal", "Skip dinner", "Generate week".
- Empty states say what is true and what to do next, in that order: a `Body variant="muted"` line plus one primary `Button`. No illustrations, no jokes about the emptiness.
- Errors say what happened and what to do, never what went wrong technically. "We couldn't save that. Try again." not "Request failed (500)."
- One light-touch phrase per screen at most. Warm is a seasoning, not the dish.
- An optional text field ends its label with "(optional)" ("(vabatahtlik)" in Estonian). Placeholders only give an example and never say it; required fields, checkboxes, radio groups and selects carry no mark, and there are no asterisks.
- A household's own item in My recipes is a **recipe**: you create, import, edit, save and delete a recipe. A **meal** is what is planned into a day's slot, or eaten: "Pick a meal", "No meal planned", "meal plan", "meal type". "Imagine a meal" keeps the word, because it imagines something to eat and what you save from it is a recipe. In Estonian: "retsept" and "toit".

## Reject list

Agents produce these by default. Recognise them and do not ship them.

- Cards nested inside cards, or a bordered wrapper around a list of bordered items (a `RowGroup` holds borderless rows)
- A sticky or floating action bar inside page content
- Page titles above `text-xl` inside the app
- Arbitrary font sizes (`text-[10px]`, `text-[13px]`)
- A raw palette class (`text-green-600`) where an existing pairing or token exists
- Neutral chrome on a tinted surface: a grey-bordered `outline` badge, a grey select trigger or a grey separator inside a meal-tinted card or the shopping note. Everything inside the tint uses the tint's tokens, and `[data-meal-surface]` re-scopes `--border` and `--input` to the chip colour for exactly this reason — so a grey line there means something escaped the tokens (a raw `border-gray-*`, a hardcoded colour). Decided 2026-09-24, after a protein badge shipped with a grey ring on a coloured card.
- A `dark:` override on a semantic token
- Gradients, glows, blurred blobs, glass effects, colored side rails, decorative shadows (the `mask-image` fade that blends a meal image into its surface excepted)
- Decorative icons or illustrations in empty states
- An emoji standing in for an icon, in a control, a label or a translated string (the shopping list's group headings excepted — see Icons under [Primitives](#primitives-we-already-have))
- An eyebrow label in all caps above every heading
- Centered hero plus a three-card grid for anything that is not the landing page
- Three or more buttons of equal weight in one row. One primary, the rest `outline` or `ghost`. The exception is a row of suggestion chips that each send a ready-made input, such as the cook view's question chips (HON-969). They are alternatives the user picks from, not actions that compete, so none is primary
- A screen's primary action rendered at `size="sm"`
- A page-level button stretched to the column width above `md`. From `md` up a button is as wide as its label and aligns to the start of its column (`w-full md:w-auto md:self-start`). Full width is for phones, and for the auth, `/onboarding` and `/invite/[code]` form cards, where the card is the form (`HON-767`'s exception, `HON-782`)
- Playful copy on more than one element per screen
- A theme or language toggle placed in the header (signed out, where there is no menu, the theme toggle in the pill is the one exception — see "Controls belong in menus, not headers")
- `transition-all`, `ease-in`, or a transition or one-shot animation longer than 300ms inside the app (looping spinners and skeletons excepted)
- An entrance, bounce, or stagger on something done many times a session (ticking an item, toggling a staple), or a staged reveal of AI output
- Motion as the only sign that something changed: a state that is visible only while its animation runs
- A placeholder, icon, skeleton, or shimmer for a missing meal image (the plain `bg-muted` box while `imageStatus` is `generating` excepted)
- Stock or decorative photography
- A second image style alongside the generated meal illustration
- A meal image framed as a photo: hard-edged, bordered, or un-blended on a tinted surface

1. ~~The Body level has no wrapping variant.~~ Resolved 2026-09-23 in HON-675: `Body variant="paragraph"` (`text-sm leading-normal`) is the wrapping foreground level, named after what it renders so a callsite never reads `<Body variant="body">`. `small` stays `leading-none` for single-line items.
